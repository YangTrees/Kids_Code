## 1 核心结论

项目已经具备继续打磨的技术基础：积木编辑、受控运行、舞台、保存恢复、课程入口、路线地图和互动面板都已存在。当前适合定位为“可内部试用的本地儿童编程产品”，还不能仅凭功能数量和自动化测试，认定已经成为教学体验成熟的课程网站。

主要矛盾是课程增长快于教学设计与体验整合。自由创作编辑器承担了几乎全部教学场景，课程描述越来越像搭建说明书，判定越来越依赖规定输出，但孩子理解目标、观察状态、解释错误和迁移应用的支持没有同步增加。

建议先停止扩充关卡总数。保留现有技术架构、角色 IP、作品与任务 ID，把下一阶段投入集中到：

1. 修复任务说明、检查清单、判定及实际地图之间的不一致。
2. 分离“跟着学”和“自由创作”的界面配置。
3. 按学习能力重组现有课程，补足预测、调试、迁移和创作环节。
4. 统一网格移动、接触与目标触发的教学语义。
5. 通过真实儿童试玩和完整发布回归验证，再扩大内容规模。

## 2 重新对齐设计初衷

原始《儿童无代码编程游戏平台产品设计说明书 V1.2》定位为 5–9 岁，进一步区分 5–7 岁启蒙和 8–9 岁进阶。核心不是学会操作一个小型专业编辑器，而是让尚未熟练识字和键盘输入的孩子，在即时反馈中创造故事与小游戏。

原需求有几个可检验的承诺：

- 少文字、大图标、短路径；一屏一件事。
- 首个正反馈在 60 秒内，10 分钟内完成首次创作闭环。
- 先获得动作反馈，再理解事件、顺序、循环、条件与调试。
- 按阶段开放能力，允许撤销和安全探索。
- 本地优先、弱网可用、刷新不轻易丢作品。

后来增加课程地图、固定路线与数据玩法，是用户明确要求的合理扩展，不应回退删除。但当前 README 的 5–12 岁定位与原需求之间缺少新的统一产品基线。

建议新版定位为：

> 面向 5–9 岁，以栗奇的互动挑战引导编程，再把学到的能力带进自己的故事和小游戏。进阶内容可供有基础的更大孩子选学。

年龄作为参考，实际入口按阅读能力与已有经验选择，不要求收集真实生日：

| 学习入口 | 建议使用者               | 默认体验                                       |
| -------- | ------------------------ | ---------------------------------------------- |
| 看图启蒙 | 识字较少、首次接触编程   | 图示目标、可选朗读、少量积木、点选参数、短脚本 |
| 编程探险 | 已懂事件、顺序和简单循环 | 变量、条件、调试、分支路线、数据实验           |
| 自由创作 | 想做自己的作品           | 完整工具、角色与场景管理、素材编辑、导出       |

不把云端、公开分享、教师后台、在线 AI 助手作为本轮的前置条件。

## 4 已有能力应当保留

- domain、block-adapter、runtime、stage、persistence 分包的方向正确；无需为了课程升级重写整个编辑器。
- AST 解释执行、运行与编辑状态分离、取消与执行上限，是安全探索的重要基础。
- 自动保存、恢复草稿、导入导出、备份与回收站，比增加新特效更有长期价值。
- 课程判定已经结合连接结构和实际运行报告，比只检查画布上有没有积木更可靠。
- 路线关已有起终点、路标、收集、步数预算和禁止回访等机制，可以继续组合。
- 分类卡片和柱状图有真实交互数据，不是静态装饰。
- 自有角色与暖色玩具感方向已有辨识度，主要需要统一尺度、层级和资源规范。

## 6 教学路线重新编排

### 6.1 难度不是每关更长

不建议将所有后期课机械增加循环次数或积木数量。较合理的节奏是：引入概念、短练习、变化应用、调试、综合挑战，再短暂回落进入新概念。后一个阶段的综合要求应高于前一个阶段，但热身允许简单。

“更难”应来自以下维度中的一两项，而不是同时全加：

- 需要自己规划的步骤增加。
- 从固定答案变成多个合理解法。
- 从已知输入变成边界值或新输入。
- 从一个事件变成多个事件协作。
- 从照示范到独立预测、找错、解释。
- 在正确基础上比较效率或表达方式。

课程页应标记“新概念 / 复习 / 调试 / 挑战 / 创作”，而不只显示一个推算出的难度标签。

### 6.2 现有 64 关处理方向

现有 taskId 和旧作品不删除。下表是内容编辑方案，不是立即更改解锁顺序的补丁；正式迁移时需给每关产出新旧版本映射。

| 当前关卡           | 处理方向                                                                                                 | 达成的能力                   |
| ------------------ | -------------------------------------------------------------------------------------------------------- | ---------------------------- |
| 1–6 基础入门       | 保留，减少首屏工具，加入运行前预测；旋转先用 90 度并说明它与屏幕方向的区别                               | 事件、顺序、方向、第一次循环 |

主线建议按“事件顺序 → 路线循环 → 互动碰撞 → 数据条件 → 多事件协作 → 自选创作”组织。初步可从现有内容中选出 24–32 个关键学习节点，其余作为复习、变式和选做；最终数量以逐关能力表与试玩结果确定，不以凑整数验收。

简单课允许通过一个短诊断跳过。保留单元试学入口，但先显示先修能力和补课路径，不把“任意单元第一课开放”当成完整学习推荐机制。

## 7 丰富玩法的具体方案

先使用现有运行时支持的机制，每次补一个可复用玩法模板，不一次性开发新游戏引擎。

| 玩法     | 例子                                     | 核心能力           | 判定重点                             |
| -------- | ---------------------------------------- | ------------------ | ------------------------------------ |
| 路线规划 | 邮递员经过两户人家后到邮局               | 顺序、循环、规划   | 路标顺序和终点；允许多条合法路线     |
| 预测结果 | 先标出角色会停在哪格，再运行验证         | 程序阅读、心智执行 | 预测与轨迹对照，不直接要求抄写程序   |
| 修复程序 | 栗奇在第二个弯走错，找出需要改的一块     | 调试、因果         | 错误消失；不给“猜哪一块”代替实际运行 |
| 规则分拣 | 水果按形状或数量分类，后加入一个边界样本 | 条件、特征         | 对多个确定样本正确；错误能解释       |
| 数据调查 | 数三片果园的果实，生成柱图并回答哪里最多 | 变量、比较、读图   | 数据来自操作；最高柱不是固定位置     |
| 模式接力 | 观察 AB、AAB 模式，编程续上并改编        | 循环、抽象         | 节拍或显示序列，而非固定台词         |
| 条件开门 | 拿到钥匙并且能量足够才开门               | AND、状态          | 两个条件四种组合都经过验证           |
| 故事接力 | 一个角色说完触发另一角色回应，再翻页     | 广播、顺序、场景   | 角色间事件关系与状态保持             |
| 创作挑战 | 做一个收集游戏、互动故事或节奏作品       | 综合应用           | 基础能力清单与可玩性；不规定唯一代码 |

优先落地顺序：预测与调试、数据读图变式、条件开门、自由创作挑战。路线系统已较丰富，不必继续靠更多路线图承担全部课程。

每个新玩法先交付“一个示例关 + 一个迁移关 + 错误反馈 + 评测测试”，再扩充同类内容。

## 8 通关判定与反馈重构

### 8.1 区分任务目标与实现方法

课程配置明确两类约束：

- 行为目标：到达目标、收齐物品、正确分类、响应消息、保持跨场景状态。
- 本课学习要求：例如必须用循环表达重复模式。这类限制必须在运行前告诉孩子。

不因多用一个安全的积木或说了不同的庆祝语就失败。也不为了接受多解而取消教学目标。若本课学习循环，就要求实际承担任务的循环执行，而非画布上另放一个无关循环。

建议使用与任务角色绑定的语义结果，不把教学结果绑定到任意 var_1；自由台词与“大小分类结果”分离。分类结果可通过标签卡或指定输出积木表达，避免要求低龄儿童精确输入一串汉字。

### 8.2 评测应与实际执行对应

目前 hasLoop、hasBranch 分别寻找结构，执行次数另行汇总。下一阶段应把证据绑定到相同的脚本、积木及作用对象，防止一个程序满足结构、另一个程序碰巧产生输出。

统一记录关键事件：积木开始/结束、移动、接触进入/离开、变量更新、分类结果、消息、场景。课程检查器消费报告，不直接操纵舞台。

对规则课使用可复现的样本集合，必须包含阈值两侧和边界；随机体验可以保留，但不能依赖三次随机恰好覆盖三种结果。测试用固定种子与样例，不让同一正确程序随机成功或失败。

每关至少准备参考解法、一个合理变式、一个相近错误解法；条件关再加边界样例。允许多解的关卡至少验证两种不同结构的正确答案。

### 8.3 反馈面向下一步行动

把“这次还差一步：用变量比较”改为可定位的反馈，例如：

- “第 4 步向右会离开道路，看看这里是不是要向上。”
- “只有大于 3 才分到大堆，数字 3 应该去哪边？”
- “你收到了消息，但宝箱没有收到。检查接收消息的名字。”
- “得分到 5 了，但程序还在重复。把停止放进满足条件的分支。”

任务卡只展示目标、一个当前问题与提示入口；完整诊断在详情里。失败不清空程序，停止恢复起点但保留上次轨迹供查看，并明确区分“再运行”“回到起点”“清空程序”。

完成奖励统一鼓励。另用“尝试过、在提示下完成、独立迁移完成”等非羞辱性状态记录学习证据；不因运行次数、耗时或看提示扣星。

## 9 网格尺度与碰撞规则

不建议再次全局缩放角色来修复所有关卡。先确定两种场景契约，尽量复用现有引擎，通过配置切换。

### 9.1 网格课程

- 格子是移动与占位单位，角色的逻辑占位点始终一致；渲染在格子之间补间，但结算落在格子中心。
- 默认一个角色占一格。角色视觉尺寸建议从格高约 0.75–0.9 的轮廓开始试调；这只是美术起点，最终看实际小屏辨认与遮挡。
- 脚底/定位点增加轻微标记，明确“站在哪格”，不要混淆整张图中心和脚底锚点。
- 起点、终点、道路、障碍、可收集物统一图例；角色与物品不能遮住关键路口。
- 路线入门优先使用屏幕上下左右。教相对朝向时，换成明确的“前进 + 左转/右转”工具包与朝向箭头，不混用解释。
- 教学模式中锁定地图、目标物与格距；允许个性化换皮，不让拖走目标物或改格距破坏评测。

### 9.2 自由创作

保留自由摆放、连续移动、造型缩放和近似碰撞，给创作者明确的属性选择：

- 装饰物：不阻挡、不触发。
- 可收集物：可进入，首次有效收集后不重复计分。
- 实体障碍：阻挡，接触边缘可触发。
- 目标区/机关：触发但是否阻挡单独定义。

“站进目标格”与“碰到实体宝箱边缘”是两种合理目标，不能在文案和判定中互换。必须针对大步长越过物体、退开再进入、隐藏、缩放、旋转、切场景和重跑建立回归。

保留现有近似矩形/圆形碰撞，不把像素级物理作为当前优先事项。先让可见规则与实际判定一致。

## 10 UI 与素材提升

### 10.1 首页和课程入口

首页从宣传页转为儿童的行动入口：首屏主操作为“继续学习”或“开始第一课”，次操作为“自由创作”；导入放到作品管理。保留现有主视觉，但减少漂浮装饰与重复课程入口。

本次 1366 宽截图中，“开始学习”“开始空白创作”“导入作品”均出现不自然断行。先修按钮宽度与文案，再讨论新增插画。

课程页默认显示当前单元与接下来几个任务，其余折叠；保留全部课程浏览入口。展示“这单元会做什么作品”和“已学会什么”，不要只展示 0/64 和长列表。

### 10.2 课程编辑器

- 顶部只突出返回、任务名、保存状态、运行、单步、停止和提示。
- 舞台附近始终有一句可读目标；高级元信息如像素、0 起始坐标默认收起。
- 仅显示本课相关积木与少量可探索积木；控制类别颜色与实际块色保持同一来源。
- 数字优先用大步进器和常用值；对象用头像，场景用缩略图；保留高级输入入口。
- 第一课提供任务内演示或半成品起点；引导在实际拖入、连接、运行后推进，可重看或跳过。
- 调试模式突出当前块、轨迹、变量变化；不要只把单步做成另一个小按钮。
- 课程模式隐藏不相关的角色/场景/声音管理，仍可从“改成自己的作品”复制到完整编辑器。

### 10.3 素材策略

不建议全量重新生成图片。当前主要问题是功能空间与画面空间不一致，而不是素材数量不足。

保留：栗奇等自有角色、已可用的透明物件、适合故事创作的森林/教室背景、已有音效。

需要改造或补充：

1. 路线地图使用统一俯视或近俯视规则；生成低干扰背景，格子、道路、路标、出口由代码精确绘制。
2. 数据课使用实验台、果园计数区、分拣区，给数据变化明确的视觉对象；不用角色静止站在风景里代替数据展示。
3. 补少量有教学用途的物品：钥匙、门、不同特征的物品、开关状态、载荷箱。先列用途再生成。
4. 栗奇仅在辨认或反馈确实需要时增加少量表情/动作；暂不制作大规模动画素材库。
5. 统一缩略图、按钮图标、关卡符号的线宽与风格。运行旗子、箭头和积木示意用 SVG/程序绘制，不用生成图片伪造控件。
6. 柱状图、数轴、真实积木示意、路径与碰撞区全部数据驱动，不生成带固定数字和文字的图片。

建议每个素材记录主题、视角、尺度、占位、锚点、碰撞属性、透明留白、缩略图、来源与审核状态。新素材先在 480×360 舞台和 1024 宽编辑器里验收，再进入库。

## 11 工程改造与兼容策略

### 11.1 课程成为有版本的数据

新增或整理课程协议：

- lessonId、contentVersion、适用路线、先修能力、学习目标。
- starterProject、工具箱白名单、可编辑范围、地图/玩法配置。
- 行为目标、教学约束、提示、失败反馈与完成回顾。
- 参考解、等价解、错误解、边界用例。
- 旧版本映射与内容变更说明。

将现有大文件按单元拆分，取消“旧任务定义 + 大量部分覆盖”作为长期维护方式。文档目录和课堂任务卡尽量从同一份配置生成；结构与枚举由 Schema 校验，涉及运行逻辑使用受控的内置评测器，不执行任意外部代码。

### 11.2 保存和学习进度

- 课程进度、题目版本、作品绑定与互动记录进入统一仓储接口，不继续分散在组件 localStorage key 中。
- 保留现有本地数据；先读旧格式，验证迁移，备份后写新格式。
- 内容升级不改变旧作品起点、脚本和已完成记录；需要新版时复制并明确说明。
- 验证多标签编辑冲突、存储写入失败、素材恢复失败与浏览器空间不足。
- 提供清楚的本地保存范围说明和定期导出提醒，不把“自动保存”等同于“永不丢失”。

### 11.3 发布质量

- 修复子路径后，开发与生产构建都验证首页、课程页、深链接刷新、资源加载和错误返回。
- CI 安装所有实际配置的浏览器，或明确分开 Chromium 回归与 WebKit 回归任务。
- 离线测试必须覆盖首次访问首页后打开编辑器、已访问作品、应用升级、素材替换与失效缓存。
- 素材版本与构建版本关联；更新应用前保存草稿并给出可恢复提示。
- 按原需求量测冷启动、缓存启动、拖拽响应、保存耗时、20 角色/500 积木与连续使用，不因 bundle warning 单独判定性能不合格。
- 恢复素材审核、第三方声明及正式发行检查。未完成审查时保持内部原型定位。
- 这里只提出安全与隐私验证工作，不宣称已完成合规或全面安全审计。

不引入后台 CMS、微服务或新的大型 UI 框架来解决本轮问题。

## 13 儿童试用与成功标准

建议由家长同意后，先安排两轮各 5–8 名目标儿童的小规模观察，覆盖识字较少与有基础两组；此样本用于发现问题，不用于宣称统计学有效的学习效果。

一次观察只安排少量目标任务：

1. 新用户是否能在没有连续口头指导下找到开始入口并完成首个动作。
2. 看完目标能否用自己的话或指图说明要做什么。
3. 遇到一次错误后，能否使用反馈修改，而不是反复乱试。
4. 能否把已学能力用于换地图、换数据或换角色后的任务。
5. 是否主动做一次有意义的改编。

记录点击/拖拽失败、求助点、误解的术语和卡住位置。默认仅保存本地枚举与计数，不采集作品正文、录音、身份信息或上传儿童行为轨迹；人工观察记录同样应最小化。

验收优先使用原需求目标：首次正反馈 60 秒内、首次创作闭环中位数 10 分钟内、首次完成率至少 70%、触控操作成功率至少 95%。这些是目标，不是当前实测结果。

另外建立产品自己的学习指标：新题迁移完成情况、提示后能否继续、同类错误是否减少。不要仅以完成了多少关、运行次数或观看时长代表学会编程。

## 14 对标时应借鉴什么

Code.org 官方教学说明将课程按年龄/年级组织，介绍了练习、挑战、后续巩固和自由创作的节奏，也明确允许使用提示。它并不要求每一题都比上一题更难。本项目应借鉴这种学习组织方式，而不是只借鉴关卡列表和星级外观。[官方教学说明](https://support.code.org/hc/en-us/articles/26001058366093-Teaching-Computer-Science-Fundamentals-Courses-A-F)

ScratchJr 面向 5–7 岁，强调孩子制作自己的互动故事和游戏。它对本项目更有价值的启示，是保持低龄操作的可理解性与创作空间，而非不断增加工具按钮。[ScratchJr 产品介绍](https://www.scratchjr.org/about/info)

上述为产品设计参考，不复制它们的品牌、课程素材或视觉资产。本项目的差异应来自栗奇世界、中文低龄体验、本地可靠创作，以及课程到自选作品的自然过渡。

## 15 本轮决策建议

保留项目，不推倒重来；将“继续增加功能”改为“先证明一条学习路线真正好用”。

近期不增加账号、公开社区、在线 AI 助手、教师后台、复杂物理、多人协作，也不把全部图片重生成。先解决任务可信、操作清晰、反馈有效和旧作品兼容，再增加少量真正改变思考方式的玩法。

这次审核的最重要结论是：下一阶段需要同时改课程设计、评价规则和交互配置。只增加难度、只换图片或只重写 CSS，都不足以解决当前体验问题。
